# 내 투자 리허설 — 실행 지시문과 검증 계획

## 실행 지시문

기존 MinchoLover/robo에 고객 문제 하나를 검증할 기능을 구현한다. 대상은 기본 ETF 구성에 관심 테마를 반영했지만 그 선택의 위험 차이를 이해하기 어려운 투자자다. 고객 가설은 ‘같은 과거 기간의 두 구성을 비교하면 자신의 선택 이유를 더 구체적으로 설명할 수 있다’이다. 수요나 지불 의사가 입증됐다고 주장하지 않는다.

사용자는 내 포트폴리오에서 리허설을 열고, 확정 당시 함께 저장한 Base와 Personalized를 같은 기간·금액으로 비교한다. 평가액 흐름, 고점 대비 하락률, 최대 낙폭을 읽고 기존 판단 검토 화면으로 돌아간다. 최초 비중·이유·예상을 덮어쓰지 않는다. 신규 계정 생성, 운영 시작일 변경, 주문, 실제 투자 권유는 범위 밖이다.

P0는 ① 소유권을 확인하는 읽기 API ② 두 구성의 동일 기준 계산 ③ 기존 다크 화면과 빈 상태·오류·모바일 대응 ④ 계산 및 실제 API 브라우저 검증이다. 서버 금융 엔진과 검증된 기존 가격 묶음을 재사용한다. 클라이언트는 금융 계산을 하지 않는다. 새 DB·분석 서비스·외부 가격 수집·전략·자동 조정·유료화 기능을 추가하지 않는다.

저장된 원본 Base가 없거나 해당 자산 가격이 없으면 미확보로 표시한다. 현재 구성이나 CORE로 대체하지 않는다. 기본 기간은 가격 묶음 전체이며, 모든 관측 연도를 동일 규칙으로 제공한다. 수익률에 따라 기간을 추천하지 않는다. 최초·최종 연도는 일부 기간임을 표시한다. 공통 관측일 31개 미만은 계산하지 않는다.

결과는 ‘확정 비중을 과거 가격에 적용한 가정 계산’으로 표시한다. 실제 운용 실적·당시 실행 가능 전략의 검증·미래 최대 손실이 아니다. 매수 후 보유, 정기 리밸런싱 없음, 소수 수량 가정, 비용·세금 제외, 현금 이자 0을 명시한다. 기존 묶음의 환율·배당 조정·대용가격 및 휴장일 전처리 한계를 공개한다. 운영 성과 API나 NAV에 기록하지 않는다.

완료는 테스트·빌드·격리 브라우저 화면·PR로 확인한다. 배포 성공과 인증 후 운영 화면 확인을 구분해 기록한다. 결과를 교수님께 설명할 때 구현 검증과 고객 효용 검증을 혼동하지 않는다.

## 인수 기준

- 동일 비중이면 평가액·낙폭이 같다. 금액 두 배는 평가액만 두 배, 수익률·낙폭은 같다.
- 기준 가격 100→120→90→110의 낙폭은 -25%, 시작금 대비 최종 수익은 +10%. 현금은 이자 0.
- 누락·비정상 가격/비중을 0 수익으로 대체하거나 일부 자산을 빼고 재정규화하지 않는다.
- 인증되지 않은 조회는 401, 타인/없는 판단은 404. 조회 전후 판단·선택·주문·거래·NAV·예약 작업이 바뀌지 않는다.
- 기간/금액을 바꾸면 새 조합의 결과만 보인다. 실패한 새 요청에 이전 조합의 수치를 붙이지 않는다.
- 화면에 실제 기간, 저장 판단 날짜, 비교 대상, 출처·자료 종료일·한계가 표시된다. 모바일 가로 넘침과 키보드 접근을 확인한다.

## 고객 검증 계획 — 아직 실시하지 않음

개발팀 밖 ETF 투자 경험자 6명을 모집해 기존 화면과 리허설 화면을 순서를 바꿔 보여준다. 테스트 계정임을 먼저 알리고, 동일 구성·동일 자료로 비교한다. 개인 자산이나 계좌 접근을 요구하지 않는다. 녹음·개인정보 저장은 별도 동의 없이 하지 않는다.

진행자는 답을 가르치지 않고 세 가지를 묻는다: ‘해당 기간에 어느 구성이 더 크게 하락했나요?’, ‘이 수치는 실제 계좌 성과인가요?’, ‘이 구성을 유지하거나 다시 검토한다면 이유는 무엇인가요?’ 정답 구별과 자발적 설명을 각각 기록하며, 유리한 발언만 추리지 않는다.

탐색적 진행 기준은 6명 중 5명 이상이 과거 가정/실적을 구분하고, 4명 이상이 구성 차이를 인용해 선택 이유를 설명하는 것. 기존 화면과 차이가 없다면 개선 효과를 주장하지 않는다. 소수 표본·진행 순서·학습 효과 한계를 기록한다. 반복 사용·지불 의사·투자 성과는 이 시험으로 입증되지 않는다.

## 교수님께 설명할 내용

기능을 늘리는 대신 고객이 사용하는 순간을 좁혔습니다. 기본 구성에 테마를 더했을 때 위험 차이를 이해하기 어렵다는 가설에 따라, 동일 과거 기간의 평가액과 낙폭을 비교하는 기능을 구현·시험합니다. 과거 계산의 정확성과 사용자 효용은 따로 검증합니다. 정상 운용 기록 및 3·6개월 관측은 기존 검증 구조에서 계속 확인해야 하며, 리허설이 이를 대체하지 않습니다.

## 실행 및 검증 기록

AI(Codex)가 실행 지시문·설계·구현·자동 검증을 수행했다. 고객 인터뷰 결과를 생성하지 않는다.

### 2026-10-25 구현 검증

- 읽기 API: `GET /api/v1/me/decisions/{decision_id}/rehearsal?period=all&initial_amount=10000000`. 인증된 본인 판단만 허용한다. `period`는 `all` 또는 응답의 연도 ID, 투자금은 1만~10억원의 정수. 화면은 100만·1,000만·1억원을 제공한다.
- `AVAILABLE`일 때 `base`, `personalized`에 저장 비중·최종 평가액·기간 수익률·최대 낙폭, `series`에 공통 날짜의 평가액·낙폭을 반환한다. `UNAVAILABLE`이면 두 결과는 null, series는 빈 배열이며 이유가 제공된다. 새 가격이나 판단을 소급 저장하지 않는다.
- `.venv/bin/python -m pytest tests --ignore=tests/backup -q`: **744 passed, 57 skipped**. 로컬에서 별도 PostgreSQL 테스트 DB 주소가 없어 관련 항목이 제외됐다. 기존 backup 전용 workflow는 수정하지 않았다.
- `cd web && npm test`: **132 passed**. 기존 판단 패널 회귀 포함. `npx tsc --noEmit`, `npm run build`: 통과. 별도 lint 스크립트는 없으며 Next 빌드의 검사를 사용했다. 동일 잠금 파일을 쓰는 기존 개발 의존성을 재사용했고 의존성을 추가·갱신하지 않았다.
- 실제 FastAPI + production Next 빌드의 브라우저 시험 **2 passed**. 원본 판단과 주문·거래·NAV·예약·검토 기록 수가 조회 전후 동일했다. 검증용 구성은 AI 테마를 포함한 신규 격리 계정이며 운영 투자 판단이 아니다.
- 모바일 화면을 직접 확인해 선택 상자가 너무 좁아지는 배치를 수정했다. 금액 축 폭을 확보했고 기간을 변경하다 통신이 실패해도 기간 선택지는 유지한다. 수치는 이전 요청의 결과로 대체하지 않는다.

### 재현

```sh
cd web
NEXT_PUBLIC_CAPSTONE_DEMO=1 NEXT_PUBLIC_LAB_MEETING=1 npm run build
cd ..
.venv/bin/python web/e2e/run_rehearsal.py
```

도구가 `/private/tmp/robo-rehearsal-*` 아래에 매번 새로운 DB를 만들고, 로컬 주소에만 연결한다. 운영 DB 설정을 비우고 기존 격리 fixture 도구를 사용한다. 계정 파일은 Git에 넣지 않는다. 서버는 종료 시 정리된다. 위 화면은 시험이 새로 생성한다.

### 아직 검증하지 않은 것

사용자 모집·이해도 관측·반복 사용·지불 의사 시험은 **미실시**다. 이 구현 및 자동 테스트가 고객 가설의 입증을 뜻하지 않는다. 비용·세금·정기 리밸런싱을 포함한 실제 운용 재현도 범위 밖이다. 운영 NAV의 정상 적립과 3·6개월 관측은 기존 운용 검증에서 별도로 확인해야 한다.
